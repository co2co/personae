- **提出版本**：v0.9.0
- **状态**：待办（纯测试重构，不动引擎）
- **动机**：引擎普适性红线要求「不针对个别剧本/角色特化」，但测试层仍绑定 DEMO 卡组真实数据——换剧本即全红，与红线精神相悖。
- **现状**：10 个测试文件硬编码角色名；`test_focus_follow`、`test_relation_gate` 直接 `store.load_card()` 依赖 `engine/data/characters/` 真实卡。当前 `pytest tests/` 的 4 个失败（`FileNotFoundError: 角色卡不存在`）即源于此。
- **方案**：改为自建 fixture（角色A/B/C），不依赖磁盘卡组；`pytest` 应可全绿。
- **关联**：DEVLOG v0.9.0 第四节（普适性清理）、第七节（遗留项）。

### S4 文档举例中立化（worldbook-guide）
- **提出版本**：v0.9.0
- **状态**：调研
- **动机**：同上普适性红线——文档举例仍用已删除剧本的角色名。

- **待定**：确认是否需要保留旧举例作教学样本（更具象），还是统一为占位名。

### S3 剧本→设定 自动导入器（大工程，规划中）
- **提出版本**：v0.6.4 之后新功能（用户构思）
- **状态**：已落地 v0.7.0（commit b9e9922）；后端路由 `POST /api/import/from-script` 收口于 v0.7.1
- **动机**：降低上手门槛——玩家脑中有好剧本，但卡在角色卡/世界书的繁琐规划。后端已对接 LLM，新增「剧本提炼」接口：固定 system prompt 防越权，LLM 从剧本语义提炼角色卡+世界书，返回结构化预览，玩家点确认即写入（零手动填表）。
- **核心结论**：LLM 不能直接改文件（无权限）；由后端中间层执行——`玩家剧本 → 后端固定 prompt 调 LLM → LLM 产出 JSON → 后端调 store.save_card/save_world 写入`。引擎已有写入入口（`POST /api/character`、`POST /api/world/<name>`）作下游复用。
- **任务分解**：
  - #9 设计提炼器 spec（固定 system prompt + JSON schema 契约 + 字段白名单）
  - #10 后端 `/api/import/from-script`（校验+调 LLM+解析+沙箱过滤，只预览不写）
  - #11 前端「从剧本导入」面板（textarea→预览→确认，确认时调现有 save 路由逐条写入）
  - #12 测试（单元：JSON 剥离/schema/白名单/防注入；e2e：真实剧本走线上矽基流动）
  - #13 收口打包（版本号+DEVLOG+zip+洗白校验）
- **安全约束**：① system prompt 固定且只取白名单字段，丢弃 schema 外一切内容（防剧本夹带指令的 prompt injection）；② 后端只写 `characters/`+`worlds/`，触不到 config/代码；③ 确认导入前校验覆盖（同名角色/世界提示）。
- **红线提示**：落地写代码（#9/#10）前需先跑挂起 30 轮对照压测（线上矽基流动可提速）；config.json 仍 assume-unchanged 锁定。
